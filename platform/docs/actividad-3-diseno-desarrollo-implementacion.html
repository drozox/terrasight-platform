Actividad 3. Diseno, desarrollo e implementacion del visor web

Esta actividad documenta el diseno, desarrollo e implementacion del visor web TerraSight para el convenio CAR Cundinamarca - WWF - Fundacion Natura. Se incluyen los requerimientos funcionales y no funcionales del sistema, los casos de uso por rol de usuario, el diseno visual de la interfaz, la arquitectura tecnica del visor y la implementacion final con sus modulos.

3.1. Diseno del sistema e interfaz de usuario

El diseno del sistema sigue el principio de separacion entre capa de datos (PostgreSQL/PostGIS), capa de aplicacion (Next.js API routes) y capa de presentacion (React con Tailwind CSS). La interfaz se organiza en modulos funcionales independientes que comparten un sistema de diseno comun (tokens, primitives, layout) y un sidebar persistente que refleja la matriz de acceso por rol.

3.1.2. Desarrollo de casos de uso

El sistema identifica tres roles principales (Administrador, Analista, Gestor) con permisos diferenciados segun la matriz de acceso final consolidada. A continuacion se documentan los casos de uso principales, sus actores y disparadores.

Actores del sistema

  • ADMIN (Ana Maria, perfil administrador del convenio): acceso total al sistema, gestion de usuarios, catalogos, configuracion y auditoria.
  • ANALISTA (perfil tecnico): consulta de datos, generacion de reportes, analisis espacial y alertas. Sin acceso a Monitoreo, Configuracion, Auditoria.
  • GESTOR (perfil de campo): actualizacion de estados de intervencion y carga de datos de monitoreo. Sin acceso a Analisis, Reportes, Alertas, Auditoria, Catalogos, Configuracion.

3.2. Desarrollo del visor web

El visor web es la pieza central de la plataforma TerraSight. Consume datos geoespaciales en formato GeoJSON desde la API de Next.js y los renderiza sobre Leaflet en el navegador. La arquitectura del visor evita servicios intermediarios (WMS/WFS) y mantiene el renderizado 100% client-side, con datos que se sirven como JSON desde la misma aplicacion Next.js.

Stack del visor

  • Next.js 15.1.6 — App Router con Server Components por default y Client Islands ("use client") solo donde se requiere estado o eventos.
  • React 19.0.0 — UI declarativa con concurrent rendering.
  • react-leaflet 5.0.0 — binding declarativo de Leaflet para React, cargado via dynamic() con ssr: false para evitar el error de Leaflet en SSR.
  • leaflet 1.9.4 — motor de rendering, ~40 KB minificado, BSD-2-Clause.
  • @types/leaflet 1.9.16 — tipos para TypeScript.
  • TypeScript 5.7.3 — strict mode en todo el visor.
  • Tailwind CSS 4.0.0 — utility-first styling para los controles del mapa (no afecta los tiles).

SRID mixto y manejo de geometrias

El visor maneja tres tipos de geometria almacenadas en sub-tablas separadas segun el modelo BDG, todas con SRID 4326 (WGS 84):

  • sgs_pro_propuesta_punto — geometry(Point, 4326). Render con <Marker> + icono coloreado segun tipo_punto.
  • sgs_pro_propuesta_linea — geometry(LineString, 4326). Render con <Polyline>.
  • sgs_pro_propuesta_poligono — geometry(Polygon, 4326). Render con <Polygon> + popup de area en ha.
SRID mixto real: los predios usan SRID 4686 (MAGNA-SIRGAS, datum oficial colombiano) y las propuestas usan SRID 4326 (WGS 84, datum GPS). El visor convierte implicitamente via Leaflet (que trabaja en WGS 84) y el backend usa ::geography para calculos geodesicos correctos en metros.

Flujo de datos del visor

  1. El usuario navega a /mapa. El server component ejecuta getPrediosGeoJSON() + getQuebradasMini() en paralelo (Promise.all) sobre postgres-js.
  2. PostGIS ejecuta ST_AsGeoJSON(geom) y devuelve un FeatureCollection.
  3. El cliente renderiza las features con <GeoJSON> o <Marker> segun tipo.
  4. El usuario interactua con capas, herramientas o busqueda. Las mutaciones (crear/editar predios) van a /predios/* (Server Actions) o /api/* (route handlers).

Patron de Server Actions

Todas las mutaciones siguen el mismo patron replicado en 15+ modulos:

  1. Verificacion de rol con await requireRole([...]) — red de seguridad server-side que bloquea el 100% de accesos no autorizados.
  2. Validacion declarativa con safeParseForm(formData, schema) — devuelve {ok, data} o {ok: false, message, field}.
  3. Ejecucion de la funcion de repository correspondiente, con try/catch para capturar errores especificos (23505 UNIQUE, 23503 FK, 23514 CHECK).
  4. Revalidacion con revalidatePath("/modulo") para invalidar cache del App Router.
  5. Mensaje util devuelto al cliente con explicacion en espanol (nunca el codigo de error crudo de Postgres).
